## Mode requirements

“Guarded sandbox” launches a managed browser process with its own isolated data directory. Two engine families support it:

- **Pure Chromium** (Chrome, Edge, Brave, Aside): isolated `--user-data-dir`, loopback proxy flags, and QUIC/WebRTC bypass restrictions.
- **Gecko** (Firefox, Zen): isolated `-no-remote -profile` directory with generated `user.js` proxy and anti-leak preferences.

“Sandbox” refers to browser data-directory and managed-process separation. It is not a virtual machine, a separate OS user, or proof of complete operating-system containment.

“Native session” reuses an existing browser sign-in. Supported pure Chromium browsers can target a specific subprofile, and launch checks compare host and gate egress beforehand. **Native-session egress matching is an observation, not a routing guarantee.** A matching exit does not establish that native-browser traffic traverses the loopback gate, so isolating the gate alone does not prove native-browser traffic has been cut off.

## Browser capability is detected

ClaudeBar classifies installed browsers into four engine tiers: pure Chromium and Gecko support both guarded sandbox and native sessions; wrapped Chromium shells (Arc, Dia) and system WebKit (Safari) use native sessions. Actual options come from scanning the installed application rather than assuming capabilities from a name alone.

For the full matrix, see [compatibility](/ClaudeBar-docs/reference/compatibility/).

## Cookie isolation is not browser-fingerprint isolation

If two profiles point at the same native browser container, they share login state; preflight (`P15`) blocks that container collision.

However, **separate subprofiles or separate `--user-data-dir` sandboxes inside the same Chromium browser do not isolate Web hardware or rendering fingerprints.** Roughly 74 of 79 observed Sift fields stay unchanged within the same browser engine, creating both graph contagion risk and active `users_per_device_id` scoring risk.

When ClaudeBar detects multiple profiles sharing one browser engine family, it raises the non-blocking `H17` overlap warning (exempted when both profiles are confirmed to belong to the same `accountUUID`). For multi-account setups, follow the ladder in [multi-account isolation and risk boundaries](/ClaudeBar-docs/guides/multi-account-isolation/): prefer one machine per account or isolated CLI first, and use different browser engines (for example, Chrome paired with Firefox or Zen) if you must run multiple Web accounts on one Mac.

## CLI and Desktop data-directory isolation

Beyond browsers, ClaudeBar isolates local state for two non-browser clients:

- **Claude Code CLI**: enabling `isolateClaudeConfigDir` assigns a dedicated `CLAUDE_CONFIG_DIR` per profile, separating `~/.claude.json` (`userID`) and settings while keeping routine work off the Web browser fingerprinting surface.
- **Claude Desktop**: managed launches use an isolated data directory (`ant-did`) so sessions do not fall back to the host default directory.

`P19` audits both CLI `userID` and Desktop `ant-did` bindings read-only without waking processes, storing only SHA-256 hashes.

## Existing sessions are observations

The session inventory classifies managed browser processes, managed desktop processes, existing logins, and unmanaged processes. Account labels and masking help inspect that inventory; a label does not turn an existing process into a managed session.

Changing the selected profile is not proof that every open window changed its identity or network route. Verify the specific launch and instance you intend to use.
