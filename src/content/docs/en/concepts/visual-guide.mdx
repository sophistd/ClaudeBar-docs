## What each part does

<DocFigure src="/ClaudeBar-docs/diagrams/architecture-en.svg" alt="System layers from profile and storage through observation and decisions to runtime control and managed connections." width={780} height={348} />

The macOS interface and CLI provide entry points. Optional system controls need separate deployment and permissions. See [architecture](/ClaudeBar-docs/concepts/architecture/) and [security boundaries](/ClaudeBar-docs/concepts/security/).


## Which route the browser takes

<DocFigure src="/ClaudeBar-docs/diagrams/routes-en.svg" alt="The guarded browser is configured to use the loopback gate. The native browser follows its existing route after an egress comparison." width={780} height={326} />

An egress match records one observation; closing the gate does not prove that the native browser is offline. See [session isolation](/ClaudeBar-docs/concepts/sessions/) for binding requirements and coverage.


## What happens after an interruption

<DocFigure src="/ClaudeBar-docs/diagrams/recovery-en.svg" alt="An armed gate enters a grace window. Matching egress resumes admission, drift isolates immediately, and expiry depends on whether a probe was rejected." width={780} height={330} />

Reusing the prior baseline in the diagram does not reverify the egress.

A profile defaults to a four-second grace window. The wait applies to new handshakes. Existing tunnels can close immediately for some interruptions, such as sleep or a network switch. An ordinary upstream interruption can leave existing tunnels in place. Use the [interactive gate model](/ClaudeBar-docs/concepts/network-egress/) to compare the outcomes.


## Where to look in the macOS app

App screenshots use fixed demo data, not live network results. The menu bar panel and the workbench sidebar show English labels; page titles and most controls inside the workbench keep the app’s Chinese labels.

### Menu bar panel

On first run, the top of the panel tracks three steps: **Proxy / Apps / Arm**. Use **Detect Proxy** to look for a local proxy, or follow the prompt card to bind a channel in Channels. **Workbench** opens the full window.

<DocFigure src="/ClaudeBar-docs/screenshots/menu-panel-firstrun-light.png" alt="First-run menu bar panel with the Proxy / Apps / Arm steps and a Detect Proxy button at the top, a prompt to connect a local proxy channel, and Workbench, Settings and Quit along the bottom." width={712} height={388} kind="screenshot" />

### Launchpad

The workbench sidebar lists **Launchpad**, **Channels** and **Preflight**, with the active channel switcher and **Settings** at the bottom. **Incidents** appears only when there is an anomaly, an isolated gate or an unread incident.

On **Launchpad** (page title **启动台**), start with the main channel’s pass card: channel name, local listener, checks passed and admission state. Below it, **我的受控入口** (my managed entries) lists each managed desktop app or browser on its own row, where you open it.

<DocFigure src="/ClaudeBar-docs/screenshots/workbench-overview-light.png" alt="Launchpad with a pass card for the US-Primary main channel, marked as admitted with 22 of 22 checks, above a managed-entries list of Claude Desktop, Google Chrome, Safari, Dia and Aside, each with an open button." width={2080} height={1360} kind="screenshot" />

### Checks and repair

**检查与修复** (checks and repair) has no permanent sidebar entry. Selecting a risk alert on Launchpad opens this page focused on that risk relation. The app also opens it when the check before a launch fails.

Read the four cards along the top: egress, checks, same egress and risks. Then pick a triggered item in **风险关系** (risk relations) on the left; each one names the checks that triggered it. Find those checks by ID in **22 项检查** (22 checks) on the right, which can be filtered by layer L1–L5. See [how to read diagnostics](/ClaudeBar-docs/guides/diagnostics/).

<DocFigure src="/ClaudeBar-docs/screenshots/workbench-topology-light.png" alt="Checks and repair in a desynced state: four cards show HK egress, 19 of 22 checks passing, the same egress at 11 endpoints and 3 risks; the risk relation list shows 3 of 17 triggered, and the layered check list marks P01 and P03 as failed." width={2080} height={1360} kind="screenshot" />

### Content preflight

**Preflight** in the sidebar opens **内容预检** (content preflight). It examines supplied text, separately from network preflight. A configured cloud stage may send that text to a model provider.

<DocFigure src="/ClaudeBar-docs/screenshots/workbench-preflight-light.png" alt="Content preflight with analysis stages from S0 tokenization to S3 semantics and a verdict across the top, sample text with rewrite and copy buttons on the left, and a risk field linking matched terms to risk categories on the right." width={2080} height={1360} kind="screenshot" />
