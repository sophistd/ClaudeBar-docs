## 模式的适用条件

「单独打开」也叫**受控沙箱**，目前支持两类内核的浏览器：

- **纯 Chromium 内核**（Chrome、Edge、Brave、Aside）：通过独立 `--user-data-dir`、回环代理参数和禁用 QUIC/WebRTC 暗道启动受管实例。
- **Gecko 独立内核**（Firefox、Zen）：通过独立 `-no-remote -profile` 目录并写入 `user.js` 代理与防漏偏好启动受管实例。

这里的隔离发生在浏览器数据目录、Cookie 和受管进程这一层，不是虚拟机，也不是独立的操作系统用户。

「用现有登录」是**原生浏览器会话**。受支持的纯 Chromium 浏览器若存在子配置档案，可绑定到指定档案；打开前会比较本机与门禁的出口身份。即使两者匹配，也无法据此确定原生浏览器的流量一定经过门禁，因此仅隔离门禁不能证明原生浏览器已经断网。

## 我的浏览器能选哪种模式？

ClaudeBar 按四档内核识别本机已安装的浏览器：纯 Chromium 与 Gecko 支持「单独打开」和「用现有登录」两种模式；基于 Chromium 的外壳封装浏览器（如 Arc、Dia）和系统 WebKit（Safari）使用原生浏览器会话。最终可选项以本机安装扫描结果为准。

具体矩阵见[兼容性](/ClaudeBar-docs/zh/reference/compatibility/)。

## Cookie 隔离不等于浏览器指纹隔离

如果两个配置档案绑定了同一个原生浏览器数据容器，它们会共享同一份登录状态，启动前检查（`P15`）会拦截这种冲突。

但需要注意：**不要以为在同一个 Chrome 里开两个子配置档案，或另开两个 Chrome 独立沙箱，就能彻底分开两个 Web 账号。** 同内核的多 Profile 或多沙箱只隔开了 Cookie 和本地存储，Web 端 Sift 采集的约 74/79 项硬件、图形渲染与内核特征仍然相同，不仅存在连坐风险，还会触发 `users_per_device_id` 主动计数加分。

ClaudeBar 检测到不同档案共用同一浏览器内核族时，会点亮 `H17` 非阻断风险提示（若确证属于同一 `accountUUID`，则按单人多浏览器正常使用豁免）。如果需要在单机管理多个账号，请按[多账号隔离与风控边界](/ClaudeBar-docs/zh/guides/multi-account-isolation/)的阶梯优先选择一机一号、隔离 CLI，或在 Web 端强制跨浏览器内核（例如 Chrome 搭配 Firefox 或 Zen）。

## CLI 与 Desktop 客户端的目录隔离

除浏览器外，ClaudeBar 还为另外两类客户端提供本地目录与设备标识隔离：

- **Claude Code CLI**：开启 `isolateClaudeConfigDir` 后，为每个档案分配独立的 `CLAUDE_CONFIG_DIR`，分开保存 `~/.claude.json`（含 `userID`）与设置，日常使用可绕开 Web 端浏览器指纹采集面。
- **Claude Desktop**：为受管实例分配独立的数据目录（隔离 `ant-did`），避免落回宿主默认目录。

两类本地标识均由 `P19` 执行零唤醒只读绑定审计，仅留存 SHA-256 哈希，不保存明文标识。

## 已经打开的窗口会被接管吗？

会话清单会区分受管的浏览器进程、受管的桌面应用进程、已有登录以及未受管的进程。账号标签和遮盖显示方便核对这些条目，管理权限取决于进程实际如何启动。

切换选中的配置档案后，要核对本次启动和实际使用的实例。已有窗口的登录状态和网络路径要逐个确认。
